# 📖 把 PDF 做成 RAG 问答助手

把《高性价比人生指南》（395 页 / 654 条建议）做成一个能提问的助手：
问它"怎么预防蘑菇中毒""被裁了能拿多少钱"，它会**从这 654 条里挑出相关的**，
读完再用人话回答你，并且**每句话都能点开核对原文**。

这不是套壳 demo，是一个真实可跑的 RAG 项目。做完它，你会真正搞懂：

- 为什么 RAG 的价值在"检索"而不是"生成"
- 为什么切分策略决定了整个系统的上限
- 怎么让大模型只依据资料回答、不瞎编

## 一、五分钟跑起来

### 第一步：确认环境（已经帮你建好了）

项目里已经有 `.venv/` 虚拟环境，装着 pypdf、numpy、openai、streamlit。
如果你换了电脑，需要重建：

```bash
cd C:\Users\Sun\Desktop\workbuddy\rag-pdf
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
```

### 第二步之前：一条不需要任何密钥的路

如果你暂时不想注册账号，可以**先把检索跑通**。项目内置了 BM25 关键词检索，
纯本地计算，不联网、不花钱：

```bash
.venv\Scripts\python.exe build_index.py --bm25-only
.venv\Scripts\python.exe search.py "怎么预防蘑菇中毒"
```

这**不是**简化版 demo。BM25 是真实在用的经典算法（Elasticsearch 的核心就是它），
也是后面"混合检索"的一半。跑完你能看到 654 条里最相关的几条被挑出来。

> 但要清楚：这一步只让**检索**能跑，**回答**仍然需要大模型密钥。
> 所以该注册还是要注册，继续往下看。

### 第二步：填密钥（唯一需要你动手的地方）

1. 打开项目里的 **`.env`** 文件（已经帮你建好了；万一删了，从 `.env.example` 复制一份改名即可）
2. 填两个密钥：

| 要填的 | 去哪拿 | 说明 |
|---|---|---|
| `EMBEDDING_API_KEY` | https://cloud.siliconflow.cn/account/ak | 硅基流动，注册送额度，`bge-m3` 目前免费 |
| `LLM_API_KEY` | https://platform.deepseek.com/api_keys | DeepSeek，注册送额度，和你 chat-app 项目同一个 |

> **为什么是两个不同的密钥？**
> 因为它们干的是两件完全不同的事：
> - embedding 模型负责"把文字变成数字"——只做数字运算，一个字的回答都不会生成
> - 大模型负责"读资料写回答"——才是有语言能力的那一个
>
> 这是初学者最容易混淆的点。初期你觉得"一个模型搞定一切"，
> 到 RAG 这里就必须拆开了：**先检索（用 embedding），再生成（用大模型）**。

### 第三步：先看切分，别急着花钱

```bash
.venv\Scripts\python.exe build_index.py --dry-run --show=2
```

`--dry-run` 只做抽取和切分，**不调用任何接口、不花一分钱**。
你会看到 654 条建议被切出来，以及统计信息。

先检查：条目数是不是 654？章节是不是 1~34？前两条内容完不完整？

**这一步很重要**。RAG 效果差，八成是切分和检索的问题，不是大模型不行。
在这里确认切得对，再去花额度。

### 第四步：正式建索引

```bash
.venv\Scripts\python.exe build_index.py
```

要调 41 次 embedding 接口，大概 1~2 分钟。跑完 `data/` 目录里会有两个文件：

```
data/
├── chunks.jsonl   ← 654 条文本（一行一条 JSON）
└── vectors.npy    ← 654 行 × 1024 列的向量矩阵
```

**这两个文件就是"索引"。** 以后每次提问都直接读它们，不用再跑 PDF。

### 第五步：先测检索，再问大模型

```bash
.venv\Scripts\python.exe search.py "怎么预防蘑菇中毒"
```

这一步**只检索、不生成**，让你看清"到底找回了哪几条、分数多少"。

项目内置三种检索方式，可以对比着看（`--mode=` 切换）：

| 模式 | 怎么找的 | 擅长 | 短板 |
|---|---|---|---|
| `vector` | 语义向量，比"意思像不像" | 问"怎么不被骗"能找到讲"诈骗"的段落 | 对精确词不够敏感 |
| `bm25` | 关键词，比"字面重不重合" | "头孢""0x0000007B" 这类精确词极准 | 不懂近义词 |
| `hybrid` | 两路都跑，用 RRF 融合排名 | **生产环境的做法** | —— |

**实测对比**（就这个文档，你也能自己复现）：

```bash
.venv\Scripts\python.exe search.py "吃头孢期间能不能喝酒" --mode=bm25
```

第 1 名直接命中第 34 章第 11 条，一字不差。但换一个问题：

```bash
.venv\Scripts\python.exe search.py "孩子发烧什么时候必须去医院" --mode=bm25
```

BM25 找不到正确的那条——因为文档里写的是"发热就医红线"，字面上跟"必须去医院"没有重叠。
**这就是关键词检索的天花板，也是为什么需要向量检索。**

跑 `hybrid` 模式时，程序会把**两路各自的前 5 名都打出来**，
你能直接看到哪一条是被哪一路找回来的。看懂这个，你就懂了混合检索。

确认找回来的确实相关之后，再上完整问答：

```bash
.venv\Scripts\python.exe ask.py "被公司裁员了能拿多少赔偿"
```

### 第六步：打开网页版

```bash
.venv\Scripts\python.exe -m streamlit run app.py
```

或者直接**双击 `start.bat`**，浏览器会自动打开。

网页版多了个关键能力：**把检索到的原文折叠展示出来**，
鼠标一点就能看到"模型是照着哪段话说的"。有这一步，你才有资格判断它是真答还是编的。

### 第七步：跑一遍检索评测（回答"效果怎么样"）

```bash
.venv\Scripts\python.exe eval_retrieval.py
```

这一步测的是**"找得准不准"**，而不是"答得好不好"。它拿 20 条口语化提问，
去比对三种检索方式谁能把"正确的那一条"排进前 5：

| 路数 | Recall@5 | MRR |
|---|---|---|
| bm25 关键词 | 85% | 0.683 |
| vector 向量 | 95% | 0.875 |
| hybrid 混合 | 95% | 0.850 |

**结果和直觉相反**：混合检索并没有跑赢纯向量，MRR 反而更低——
因为两路都命中同一条时，RRF 融合会把原本排第一的往后挤。

所以本项目保留了三种模式可切换，而不是默认宣称"混合最好"。
换一份新文档，先跑这个脚本看数字，再决定用哪种。
（评测集写在脚本里的 `CASES`，一条一行"问题 → 正确条目标题开头"，自己加很方便。）

## 二、RAG 到底是什么

**一句话：让大模型"翻着资料回答"，而不是"凭记忆瞎答"。**

大模型有两个硬伤：

1. **不知道你的私有资料**。它训练时没见过这份 PDF，你直接问它，它只会瞎编。
2. **会一本正经地编**（幻觉）。而且编得越像真的越危险——你没法分辨。

RAG 的思路很朴素：既然模型不会背，那每次提问前，**先从资料里把相关的几段找出来**，
连同问题一起塞给它，让它"看着材料作答"。

于是整个系统分成两个阶段，这个项目的文件名就是按这个顺序排的：

```
阶段一 · 建索引（离线跑一次）
    PDF ──→ 抽文字 ──→ 洗干净 ──→ 切成条 ──→ 变成向量 ──→ 存盘
                                                        build_index.py

阶段二 · 问答（每次提问都跑）
    问题 ──→ 变成向量 ──→ 找出最像的 5 条 ──→ 拼进提示词 ──→ 大模型写回答
                                    ↑
                              search.py（只看这一步）
                              ask.py / app.py（走完全程）
```

### 关键在"找"这一步

"找出最像的几条"靠的是**向量**。embedding 模型把一段文字压成一串数字（本项目的 bge-m3 是 1024 个浮点数），
它的神奇之处在于：**语义相近的文本，数字也相近**。

所以：
- 建索引时，654 条建议全变成 654 个向量，存成矩阵
- 提问时，问题也变成一个向量
- 算它和 654 个向量的相似度，取最高的 5 个

就这。没有魔法。`rag.py` 里这行代码就是全部：

```python
scores = vectors @ qvec          # 一个矩阵乘法，得到 654 个相似度
order = np.argsort(-scores)[:k]  # 从大到小排，取前 k 个
```

> **一个小细节**：建索引时每个向量都做了 L2 归一化（除以自己的长度）。
> 归一化后向量长度都是 1，于是"余弦相似度"就等于"点积"，
> 一个矩阵乘法就能算完，而且分数天然落在 -1~1 之间，一眼能看出相关性高低。

## 三、项目结构（五个文件就是五步）

```
rag-pdf/
├── rag.py            ← 【教材】所有 RAG 逻辑，按流程排好，先读这个
│
├── build_index.py    ← 第 1 步：建索引（读 PDF → 切 → 关键词索引 → 向量化 → 存盘）
├── search.py         ← 第 2 步：只检索，看找得准不准，不花大模型的钱
├── eval_retrieval.py ← 第 3 步：检索评测，三路对比 Recall@5 / MRR（回答"效果怎么样"）
├── ask.py            ← 第 4 步：完整问答（命令行版）
├── app.py            ← 第 5 步：完整问答（网页版）
│
├── data/             ← 索引存这里（自动生成）
│   ├── chunks.jsonl   654 条文本
│   ├── bm25.pkl       关键词索引（纯本地，不需要密钥）
│   └── vectors.npy    向量矩阵（需要 embedding 密钥）
├── .env              ← 你的密钥（已建好，填两个值即可）
├── start.bat         ← 双击启动网页版
└── requirements.txt
```

**读代码的顺序**：直接打开 `rag.py`，从头往下读。
里面的函数顺序就是 RAG 的执行顺序，每个函数都有注释讲"为什么这么做"。

其余四个文件几乎没有逻辑，它们只是"遥控器"——
`ask.py` 的全部内容就是调 `rag.answer()` 然后打印出来。
理解 `rag.py` 就等于理解了整个项目。

`rag.py` 里的关键函数：

| 阶段 | 函数 | 干什么 |
|---|---|---|
| 建索引 | `extract_pages()` | 读 PDF，一页页抽出文字 |
| | `clean_page()` | 洗掉页眉页脚 |
| | `split_into_chunks()` | **把正文切成一条条 chunk（最关键）** |
| | `embed_texts()` | 把文字变成向量（调接口） |
| | `build_index()` | 串起上面几步，存盘 |
| 检索 | `tokenize()` | 极简中文分词（单字 + bigram） |
| | `BM25` | 关键词检索算法 |
| | `rrf()` | 把两路召回结果融合成一个排名 |
| | `search()` | **统一检索入口**，支持三种模式 |
| | `search_detail()` | 同上，但额外返回每路各自的排名（调试用） |
| 生成 | `answer()` | 拼提示词，交给大模型生成回答 |

## 四、最重要的设计：为什么按"条"切

这是整个项目里唯一需要动脑子的地方，也是面试最容易被问到的地方。

### 新手会怎么做

网上教程千篇一律：`RecursiveCharacterTextSplitter(chunk_size=500, chunk_overlap=50)`，
每 500 字一刀，切完事。

对这份文档，那样切会出什么后果？

| 问题 | 后果 |
|---|---|
| 一条建议的成本、收益、来源被切到不同 chunk 里 | 模型只看到"证据等级：A"，却不知道说的是哪条 |
| 一句话被拦腰砍断 | 检索出来的是残句，模型读不懂 |
| 章节标题混进正文 | 噪音污染向量 |

### 这个项目怎么做

先观察文档：**654 条建议，每条都以「• 成本：」开头**，字段固定是
`成本 / 说人话 / 收益 / 证据等级 / 来源 / 备注`。

这就是作者免费送给你的天然边界。于是切分算法变成三步：

```
1. 找出所有「• 成本：」行        →  654 个，就是 654 条的分界
2. 从每个锚点往前回溯，找到「数字.」开头的行  →  那就是条目标题
3. 一条 chunk = 本次标题起点 → 下一条标题起点之前
```

一条建议 = 一个 chunk，语义完全自足。检索命中一条，模型拿到的是完整信息。

### 通用规则（记这个，比记代码有用）

> **切分要顺着文档自身的结构走。**
> 编号、标题、空行、Markdown 的 `##`，都是作者给你的免费边界。
> 实在找不到结构，才退回去按字数切 + 加重叠。

### 真实数据逼出来的三个坑

写这段代码时踩了三个坑，都写进注释了，值得一看：

**坑 1：长标题会折行**

PDF 排版时，长标题会折成两行：

```
39. 65 岁以上的女性去做一次双能 X 线骨密度检查，绝经后有骨质疏松危险因素的不用等到
65 岁                          ← 这是标题的续行，不是正文
• 成本：去医院做一次双能 X 线骨密度检查……
```

如果只"看上一行"判断是不是标题，这条就会被漏掉。正确做法是从锚点**往前回溯最多 5 行**，
遇到「数字.」开头才停。踩这个坑的时候，我漏掉了 63 条。

**坑 2：正文里的数字会被误判成章节**

正文里有 DOI（`10.1056/NEJMoa1408544`）和统计值（`1.27（1.18 到 1.37）`），
一不小心就被当成章节标题。解法是要求**编号和名字之间必须有空格**——
真章节是 `1. 不要早死`（有空格），DOI 和统计值没有。

**坑 3：文档尾部有附录**

最后一条建议后面直接跟着 900 行附录长文，导致最后一条 chunk 膨胀到 3 万字符。
解法是加一道长度保护：超过 6000 字符就在段落边界截断。

> 这三个坑说明一件事：**真实文档永远比教程脏**。
> 处理脏数据的代码量，往往比"算法"本身多得多。这也是最能写进简历的部分。

## 五、出问题了怎么查

**排查顺序永远是：先查检索，再查生成。** 九成问题出在检索。

| 现象 | 八成的原因 | 怎么办 |
|---|---|---|
| 报错说密钥没填 | `.env` 没建、或名字写成了 `.env.txt` | 检查文件名，确认没有隐藏后缀 |
| 报错 `找不到文件` | `.env` 里的 `PDF_PATH` 路径不对 | 改成 PDF 的真实路径 |
| 检索出来的明显不相关 | embedding 模型不对 | 换 `BAAI/bge-m3`，中文效果明显更好 |
| 相关的没被找回来 | top_k 太小 / 切分不合理 | 把 top_k 调到 8 试试；再检查切分 |
| 回答里出现了资料里没有的东西 | 提示词约束不够 | 改 `rag.py` 里的 `SYSTEM_PROMPT`，把规则写得更硬 |
| 回答总是"资料里没有提到" | 检索没找到正确资料 | 还是先查检索 |
| 网页报 `还没有建索引` | 没跑 `build_index.py` | 先跑建索引 |

### 一个通用调试技巧

**把 top_k 开到 10，跑 search.py，人眼看。**

如果 10 条里都找不到能回答问题的内容，那问题 100% 在检索，跟大模型一点关系都没有。
这时候去调提示词、换大模型，全是白费力气。

## 六、进阶任务

按难度排序，做完一个就往简历上添一行。

**1. 按证据等级筛选**（简单）
文档里每条都有 A/B/C 证据等级，`rag.py` 已经把它抽到元数据里了。
在 `search()` 里加个参数，支持"只搜 A 级证据的建议"。

**2. 调混合检索的权重**（简单，代码已就绪）
混合检索已经实现了，但两路权重现在是 1:1。
实际上问题类型不同，最优权重也不同：问"头孢"这类精确词，BM25 该占更大权重；
问"怎么防止被骗"这类语义问题，向量该占更大权重。
`rag.py` 的 `rrf()` 支持传 `weights`，试试改成 `[0.4, 1.0]`，看结果怎么变。
**能说清"为什么这样调权重"，比调对更重要。**

**3. 加一层重排序**（中等）
混合检索已经做到了"召回 20 条"，但精排还是靠融合分。
可以再接一个专门的 rerank 模型精排出前 5 条，硅基流动就提供 rerank 接口。

**4. 建评估集**（✅ 已完成，见 `eval_retrieval.py`）
本来要手动写 30 个问题、标好每题的正确答案在哪几条。**现在已经建好了 20 题**，
跑一次 10 秒，三路检索的 Recall@5 / MRR 直接出表。
后续每次改参数（切分方式、top_k、检索模式、权重）都跑一遍，看数字怎么动。
**没有评估集，你改参数全靠感觉，等于瞎调。**
想扩到 30 题很简单：打开脚本往 `CASES` 里加一行 `("口语化提问", "正确条目标题开头")` 即可。

**5. 多轮对话**（中等）
现在每次提问是独立的。加上多轮后，用户问"那第二条呢"就答不出来了——
因为"第二条"这个指代没头没尾。
解法是先用大模型把追问改写成独立问句，再去检索。

别写"使用 LangChain 搭建 RAG 系统"——这句话谁都能写，面试官一眼扫过。

要写出**问题、取舍、数字**：

> **《高性价比人生指南》私有知识库问答助手**（个人项目）
> Python / 向量检索 / Streamlit / 大模型 API
>
> - 从 395 页 PDF 构建 654 条结构化知识索引，按文档自身结构设计切分策略，
>   替代固定长度切分，保证每条知识的成本、收益、来源等字段完整不割裂
> - 处理真实 PDF 的脏数据问题：跨行标题回溯匹配、页眉页脚清洗、
>   正文数字与章节标题的误判排除、尾部附录异常长度截断
> - 设计带引用溯源的问答链路，答案可逐条定位到原文，机制上抑制模型幻觉
> - 自建 20 题口语化评测集（人工标注正确条目），对三路检索做 Recall@5 / MRR 对照：
>   BM25 85% / 向量 95% / 混合 95%（MRR 0.683 / 0.875 / 0.850）；
>   实测发现混合检索并未优于纯向量、MRR 反被 RRF 融合打散，据此保留三路可切换并固化评测脚本

**这些数字都是 `eval_retrieval.py` 跑出来的，被追问"怎么算的"就直接把脚本打开。**
真实、可复现的数字，比上面所有的形容词都值钱。

## 附：技术栈一览

| 环节 | 用了什么 | 为什么选它 |
|---|---|---|
| PDF 解析 | pypdf | 纯 Python，无需外部依赖，能处理文字版 PDF |
| 切分 | 自己写的（`rag.py`） | 按文档结构切，效果远好于固定长度切分 |
| 关键词检索 | 自己实现的 BM25 | 纯本地零依赖，零成本，且是混合检索的一半 |
| Embedding | 硅基流动 `BAAI/bge-m3` | 中文表现好，注册免费 |
| 向量存储 | numpy + `.npy` | 654 条数据用不上向量数据库，一个矩阵乘法就够，还便于理解原理 |
| 结果融合 | RRF | 不受量纲影响，工业界标准做法 |
| 大模型 | DeepSeek `deepseek-chat` | 便宜，中文好 |
| 界面 | Streamlit | 几十行就能出网页 |

> **为什么不用 Chroma / FAISS / LangChain？**
> 因为 654 条数据，用 numpy 算余弦相似度只要几毫秒，
> 引入向量数据库只是徒增依赖和黑盒。
> **先用最朴素的方式跑通、看懂，再换工具。**
> 知道"什么时候不需要用工具"，比会用工具更能体现你的判断力。
>
> 什么时候真的需要向量库？数据量到 10 万条以上、需要增量更新、需要多进程共享索引的时候。
